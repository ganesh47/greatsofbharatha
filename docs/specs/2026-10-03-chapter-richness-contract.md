## Typed content API

The source contract is `GreatsOfBharatha/Shared/Models/ChapterKnowledgeModels.swift`. All types are value types conforming to `Sendable`; content workers use their synthesized memberwise initializers.

- `ChapterKnowledgeCitation(sourceID: String, locator: String)` uses the eight source IDs in the ledger. It does not contain a copied textbook passage.
- `ChapterKnowledgeClaim(id: String, kind: ChapterKnowledgeClaimKind, statement: String, citations: [ChapterKnowledgeCitation], taughtBeatIDs: [String], reviewStatus: ChapterKnowledgeReviewStatus)` preserves the ledger claim ID, classification, and locator. New unreviewed claims use `.pendingIndependentReview`; the current cleared catalog uses `.approved`.
- `ChapterKnowledgeBeat(id: String, title: String, text: String, claimIDs: [String])` contains original child teaching copy. The three legacy IDs are `<sceneID>-story`, `<sceneID>-memory`, and `<sceneID>-meaning`. New overflow beats use distinct stable IDs such as `<sceneID>-knowledge-water-storage`; report any updated taught-beat mapping.
- `ChapterKnowledgeChoice(id: String, text: String)` preserves the question-choice IDs in coverage. Text may be edited without reusing an ID for a different answer.
- `ChapterKnowledgeQuestion(id: String, kind: ChapterKnowledgeQuestionKind, prompt: String, choices: [ChapterKnowledgeChoice], correctChoiceID: String, claimIDs: [String], requiredBeatIDs: [String], explanation: String, hints: [String], retryFeedback: String)` follows coverage. Hints are authored support; no wrong-answer haptic or shaming copy.
- `ChapterKnowledgeDefinition(sceneID: String, claims: [ChapterKnowledgeClaim], beats: [ChapterKnowledgeBeat], questions: [ChapterKnowledgeQuestion])` returns `validationIssues` for duplicate IDs, missing legacy beats, unresolved claim references, empty copy, invalid correct choices, and incorrect teaching coverage.
- `questionsEligible(afterShownBeatIDs: Set<String>, taughtClaimIDs: Set<String>)` fails closed for an invalid catalog, pending/held claims, reflection/tradition claims, unseen required beats, or untaught facts. Source structure checks do not establish historical truth or independent learning.

Claim classifications are `.historical`, `.siteFeature`, `.vocabulary`, `.derivedReasoning`, `.tradition`, and `.reflection`. Question kinds are `.identity`, `.geography`, `.sequence`, `.meaning`, `.application`, `.material`, `.numericCount`, `.numericDate`, and `.numericYearLabelGap`. Claim review statuses are `.pendingIndependentReview`, `.approved`, and `.held`.

## Durable state and resume obligations

These obligations are implemented by the durable APIs below. Platform views commit through these hooks; source and runtime evidence are recorded separately.

The durable APIs now exist in `ChapterKnowledgeJourney.swift` and `ChapterKnowledgeAdapters.swift`. Platform workers can implement the new owned views against them without editing roots or stores:

- iOS teaching entry: `ChapterKnowledgeTeachingView(scene: LearnQuizPilotScene, definition: ChapterKnowledgeDefinition, sessionID: UUID, hooks: ChapterKnowledgeHooks, onFinished: () -> Void)`.
- TV teaching entry: `TVChapterKnowledgeTeachingView(chapter: TVChapter, definition: ChapterKnowledgeDefinition, sessionID: UUID, hooks: ChapterKnowledgeHooks, onFinished: () -> Void)`.
- Practice entries: `ChapterKnowledgePracticeView` / `TVChapterKnowledgePracticeView` accept `definition`, `sessionID`, `hooks`, `onNeedsTeaching: (Set<String>) -> Void`, and `onFinished: () -> Void`. The TV entry uses `.sharedFamilyRecognition`; iOS uses `.individualRecognition`. Add injectable `now: () -> Date = Date.init` if useful to test.
- Load with `hooks.load()`. Before starting/resuming/replacing an activity, call `ChapterKnowledgePersistence.saveAndReplay(loaded, hooks:)`; if the result is nil or still has pending evidence, expose Retry and block dependent actions. An unsupported archive (`isSupported == false`) stays read-only.
- `ChapterKnowledgeJourney.begin`, `resume`, `select`, `requestHelp`, `check`, `tryAgain`, and `advance` return proposed value archives. Commit through `saveAndReplay` and display only the confirmed result. Selection, help, and Back-clearing create no evidence. Do not drop another scene’s outbox or reset its checkpoint.
- Teaching uses `presentedBeat(beatID, visibleClaimIDs: Set<String>, sessionID:, archive:, definition:, now:)` only after the actual fact copy is presented. Partial/offscreen content cannot qualify. Preserve the active stable beat and save before calling `onFinished`. Save the supplied session rather than generating a new one on each appearance.
- `activateTeachingBeat(beatID, archive:, definition:)` saves only the stable active position, with no shown/taught IDs or evidence. Commit it through the same confirmed save/replay path. Direct checkpoint updates with this same behavior are valid provided unsupported archives and pending outboxes remain blocked.
- `archive.teachingBySceneID[sceneID]` contains `activeBeatID`, `shownBeatIDs`, and `taughtClaimIDs`. `archive.practiceBySceneID[sceneID]` contains the saved queue, cursor, phase, selected choice, response context, current turn/result, sticky help, and `canTryAgain`.
- Phase `.needsTeaching` must offer the current question’s required beat IDs through `onNeedsTeaching`, then reload/replay/resume after return. `.unavailable` retains the old queue and offers return to the story; it does not silently skip retired/held content. `.complete` is bounded completion, not a mastery claim. An explicit practice-again action passes `restartCompleted: true`; repeated questions remain seen-answer recognition.
- On every checked result, show the authored explanation (including after an incorrect choice), so the engine’s subsequent `answerSeen` support is truthful. After three incorrect attempts, offer teaching and moving on; no shaming counter or false success. Do not automatically advance a selection or checked result.
- The bridge is `ChapterKnowledgeAdapters.hooks(store: appModel.lessonStore, definitions: [ChapterKnowledgeDefinition])`. The coordinator supplies the shared catalog and integrates the parent callbacks. Known recognition is recorded with `.recognitionChoice` and explicit individual/family participation, never a typed recall witness or later-recall award.
